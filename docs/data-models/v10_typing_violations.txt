PBM MODEL v10 TYPING VIOLATIONS — Column-by-Column Audit
=========================================================================
Audited: 3147 attributes across 6 domains (claim, drug, client, company,
division, program) against pbm-reference.md industry standards.
=========================================================================

--- CRITICAL (data loss — leading zeros destroyed or precision lost) ---

1. drug.ndc.ndc_labeler_code_fk
   Current: BIGINT  ->  Required: STRING (or rename)
   Reason: Column name contains "ndc_labeler_code" which is an NDC
   component (5-digit labeler, e.g., "00069"). Typed as BIGINT, leading
   zeros are silently destroyed. The FK target is drug.manufacturer which
   is a surrogate BIGINT, so the column name is misleading — if it holds
   an actual labeler code, it MUST be STRING; if it's purely a surrogate
   FK to manufacturer, it should be renamed to labeler_manufacturer_id.

2. drug.ndc.ndc_labeler_fk
   Current: BIGINT  ->  Required: STRING (or rename)
   Reason: Same issue as #1. Column name implies NDC labeler code but
   FK target is drug.manufacturer.manufacturer_id (a surrogate). If this
   holds the actual 5-digit labeler code, STRING is mandatory. If it's a
   redundant surrogate FK to manufacturer, rename to drop the misleading
   "ndc_labeler" prefix. Currently there are FIVE FK columns on drug.ndc
   pointing to drug.manufacturer (labeler_manufacturer_id, manufacturer_id,
   ndc_labeler_code_fk, ndc_labeler_fk, ndc_manufacturer_id) — this was
   already flagged in next_vibes_v9 static analysis.

3. drug.ndc.awp
   Current: NUMERIC  ->  Required: DECIMAL(12,4)
   Reason: AWP (Average Wholesale Price) is a financial field requiring
   exact decimal precision. NUMERIC is an alias but DECIMAL is the explicit
   Databricks/industry convention. Already flagged in vibes_v6.

4. drug.ndc.wac
   Current: NUMERIC  ->  Required: DECIMAL(12,4)
   Reason: WAC (Wholesale Acquisition Cost) — same as AWP above.

--- HIGH (interop risk, type mismatch, or identifier convention) ---

5. drug.pharmacy_network.ncpdp_id
   Current: BIGINT  ->  Required: STRING
   Reason: Column name is "ncpdp_id" and it has NO foreign_key_to defined
   (it's an unlinked FK per next_vibes_v9 static analysis). The tag says
   "renamed_from=pharmacy_id,business_role=primary_dispensing". If this
   holds a 7-digit NCPDP Provider ID, it MUST be STRING (leading zeros).
   If it's a surrogate FK to drug.pharmacy, it should be renamed to
   pharmacy_id (BIGINT) and properly linked. Currently ambiguous AND
   wrong type for either interpretation.

6. drug.pharmacy_network.pharmacy_ncpdp_id
   Current: BIGINT  ->  Required: STRING (or rename to pharmacy_id)
   Reason: Same class of issue. Column name implies an NCPDP number but
   is typed as BIGINT. If it holds the actual NCPDP number, STRING is
   mandatory. If it's a surrogate FK to drug.pharmacy, rename to
   pharmacy_id. Currently unlinked per static analysis.

7. claim.rx_claim.ncpdp_id
   Current: BIGINT  ->  Required: STRING (or rename)
   Reason: FK points to drug.pharmacy.ncpdp_id. The target column
   drug.pharmacy.ncpdp_id is typed VARCHAR (correct). But this FK column
   is BIGINT, creating a type mismatch. If this is meant to be a surrogate
   FK to the pharmacy table, it should be pharmacy_id BIGINT pointing to
   drug.pharmacy.pharmacy_id. If it holds the actual NCPDP number, it
   must be STRING.

8. client.audit_finding.ncpdp_id
   Current: BIGINT  ->  Required: STRING (or rename)
   Reason: FK points to drug.pharmacy.ncpdp_id. Same issue as #7 — type
   mismatch between BIGINT FK and VARCHAR target.

9. claim.dur_event.ncpdp_id
   Current: BIGINT  ->  Required: STRING (or rename)
   Reason: FK points to drug.pharmacy.ncpdp_id. Same class of issue as
   #7 and #8.

10. program.contract_pharmacy_340b.pharmacy_id
    Current: BIGINT  FK-> drug.pharmacy.ncpdp_id
    Required: BIGINT FK-> drug.pharmacy.pharmacy_id (or STRING if targeting ncpdp_id)
    Reason: FK type mismatch. pharmacy_id is BIGINT but targets
    drug.pharmacy.ncpdp_id which is VARCHAR. Should target the surrogate
    PK drug.pharmacy.pharmacy_id instead.

--- NAMING ISSUES (not type violations but create type confusion) ---

N1. drug.ndc has 5 FK columns to drug.manufacturer:
    labeler_manufacturer_id, manufacturer_id, ndc_labeler_code_fk,
    ndc_labeler_fk, ndc_manufacturer_id
    Already flagged in next_vibes_v9 static analysis. The "ndc_" prefixed
    columns violate FK naming convention and create type ambiguity.

N2. drug.pharmacy has both ncpdp_number (STRING) and ncpdp_id (VARCHAR):
    Two columns holding the same NCPDP identifier. Redundant per
    next_vibes_v9 static analysis finding [SA:denormalized_natural_key].

N3. claim.dur_event.dispensed_ndc_id: name implies surrogate (BIGINT)
    but holds NDC value (VARCHAR FK-> drug.ndc.ndc_code). Should be
    dispensed_ndc_code.

N4. program.copay_assistance_program.ndc_id and
    program.patient_assistance_program.ndc_id: names imply surrogate FK
    but FK target is drug.ndc.ndc_code (the string natural key). Should
    be ndc_code for consistency.

=========================================================================
SUMMARY
=========================================================================

  CRITICAL violations:  4  (2 NDC/naming ambiguity, 2 pricing precision)
  HIGH violations:      6  (5 NCPDP type mismatches, 1 FK target mismatch)
  Naming issues:        4  (create type confusion but not data loss)
  Confirmed correct:   80+ fields checked, properly typed

The model is SUBSTANTIALLY better typed than initially feared. Most
identifiers (NDC, NPI, GPI, DEA, MBI, taxonomy, DAW, claim_number,
rx_number, ZIP, gender, claim_status, brand_generic) are correctly
STRING. The main issues cluster around:

1. NCPDP columns: 5 of 6 violations involve ncpdp_id columns typed as
   BIGINT instead of STRING, or BIGINT FKs targeting VARCHAR columns.
   This is the single biggest class of bug.

2. NDC manufacturer FKs: 2 columns on drug.ndc have names implying NDC
   labeler codes but are actually surrogate FKs to manufacturer. The
   naming creates ambiguity about whether the column holds an identifier
   (needs STRING) or a surrogate (BIGINT is fine).

3. AWP/WAC: 2 columns are NUMERIC instead of DECIMAL (known from v6).
